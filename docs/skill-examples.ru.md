# Примеры скилла Deckmate

Это примеры запросов и результатов, а не отчёты о выполненной работе. Для CLI нужен Node.js 26+. В `--data "<project>"` указывайте абсолютный путь к проекту; перед запуском замените все `<…>` реальными значениями. Вызовы MCP предполагают подключение сервера к тому же проекту. Ссылки на карточки, вопросы, Journey и ID колод берите из вывода, а ID участников — из реестра проекта; для первоначального шаблона выберите ID и затем зарегистрируйте его. Для каждого типа карточки выбирайте совместимую существующую колоду. Подробности: [роутер скилла](../skills/deckmate/SKILL.md), [справочник CLI](../skills/deckmate/references/cli.md) и [справочник MCP](mcp.md).

До записи согласуйте конкретный список карточек и их размещение. Прочитайте нужные диапазоны `readNext`, в том числе при сокращённом брифе. Текст карточки меняйте через интерфейс или защищённый [HTTP-запрос](../skills/deckmate/references/api.md#card-content), а не прямой правкой файла карточки. Файлы отчётов должны быть в UTF-8, заголовки — уровня `#####` или глубже. Назначение ответственного не добавляет Task в Hand и не запускает агента.

## start

**Когда:** Создать доску новой игры из стартового шаблона жанра.

**Просьба:** «Подготовь доску для моей двумерной экшен-игры на Godot и небольшой первый играбельный срез».

**Шаги:**
1. Получить список шаблонов: `deckmate project init --data "<project>"`; посмотреть план: `deckmate project init action --dry --data "<project>"`. Согласовать шаблон и его состав.
2. После согласования применить `deckmate project init action --member "<member>" --data "<project>"`, проверить `warnings` и `remaining`, затем [установить скилл](skills.md#install-and-use). Зарегистрировать участников и записать согласованный профиль.
3. Предложить один Hero первого играбельного среза и 3–5 проверяемых Task; после согласования создать их, как в [plan](#plan). Добавить Task в Hand через интерфейс и проверить `deckmate project hand "<member>" --data "<project>"`.

**Результат:** Стартовая доска с Journey и Hero «First playable» с согласованными Task.

## profile

**Когда:** Зафиксировать недостающий или устаревший контекст проекта.

**Просьба:** «Опиши наше автономное приложение учёта времени, чтобы у доски была понятная цель».

**Шаги:**
1. Прочитать профиль и документы проекта; команда `deckmate project map --data "<project>"` поможет определить доску и её источники. Спросить о недостающих пользователях, платформе, ограничениях, ориентирах и целях, а не угадывать.
2. Показать предлагаемый `tasks/deckmate-project.md`; после согласования записать его, оставив неизвестные поля пустыми. Для программного продукта без подходящего справочника жанра оставить `genre` пустым.

**Результат:** В профиле зафиксированы задача и цель приложения; карточки не созданы и не перемещены.

## plan

**Когда:** Разделить функцию на независимо проверяемые задачи.

**Просьба:** «Разбей экспорт JSON в приложении учёта времени на задачи, которые можно проверить».

**Шаги:**
1. Выполнить `deckmate project map --data "<project>"` и `deckmate project find "export" --fields brief --limit 20 --data "<project>"`; изучить совпадения и избежать дублей.
2. Предложить Hero «Export snapshot» с Task «Export JSON» и «Test export», их ответственными, колодами, оценками, зависимостями и проверками; получить согласование. Подготовить UTF-8-файл тела первой Task с разделами Visible, Work и Done, например: «Экспортировать три тестовые записи; тест экспорта проекта должен пройти».
3. Создать Hero командой `deckmate project create "Export snapshot" --kind hero --deck "<asset-or-mixed-deck-id>" --member "<member>" --data "<project>"`. Взять его ссылку из `created`, затем создать Task командой `deckmate project create "Export JSON" --kind task --deck "<task-or-mixed-deck-id>" --parent "<hero-ref>" --owner "<owner-label>" --effort 1 --priority medium --body-file "<body-file>" --member "<member>" --data "<project>"`; повторить для второй согласованной Task. Согласованные зависимости задать в интерфейсе.
4. Проверить дочерние карточки через `deckmate project show "<hero-ref>" --data "<project>"`, а предупреждения — через `deckmate project map --data "<project>"`.

**Результат:** Один Hero экспорта связывает две Task с отдельными проверками; работа над ними ещё не начата.

## milestone

**Когда:** Запланировать поставку к дате или закрыть Run.

**Просьба:** «Запланируй первый выпуск приложения на 2026-12-04 с запасом времени».

**Шаги:**
1. Согласовать объём выпуска, доступность участников и дату. Выполнить `deckmate project summary --limit 100 --fields brief --data "<project>"` и `deckmate project find --deck "<deck-id>" --fields brief --limit 100 --data "<project>"`; проверить блокировки и неоценённую работу.
2. Предложить milestone, цель Run, назначения и допущения о доступном времени. После согласования создать milestone и Runs и назначить каждую карточку в Timeline; команды project для этих записей нет. При закрытии Run согласовать переносы и причины перед Finish Run.

**Результат:** В Timeline видны согласованные milestone выпуска, цель Run и явные назначения карточек.

## work

**Когда:** Выполнить согласованную Task из Hand участника или доработать возвращённую.

**Просьба:** «Возьми следующую задачу по экспорту и отправь результат на проверку».

**Шаги:**
1. Добавить Task в Hand участника через интерфейс. Выполнить `deckmate project next "<member>" --data "<project>"`; сначала внести ожидающее решение, если оно есть. Если готовой карточки нет, остановиться, не беря несогласованную работу.
2. Прочитать `deckmate project brief "<c-ref>" --budget 1500 --data "<project>"` и необходимые диапазоны, например `deckmate project show "<c-ref>" --lines "<a-b>" --data "<project>"` для диапазона в файле этой карточки; для остальных использовать соответствующую карточку или читать диапазон источника напрямую. Сохранить исходное состояние и проверить критерии Task.
3. При начале работы выполнить `deckmate project state "<c-ref>" started --member "<member>" --data "<project>"`. Выполнить согласованное и запустить проверки; при блокировке использовать [ask](#ask).
4. Сохранить отчёт с подтверждениями и отправить `deckmate project report "<c-ref>" --file "<report.md>" --member "<member>" --state review --data "<project>"`. Проверить предупреждения и оставить приёмку уполномоченному проверяющему.

**Результат:** «Export JSON» находится в `review`, к ней приложен отчёт с результатами проверок.

## ask

**Когда:** Для продолжения работы по карточке нужно решение человека.

**Просьба:** «Спроси, какую частоту кадров должна выдавать сцена порта, прежде чем продолжать».

**Шаги:**
1. Прочитать карточку командой `deckmate project brief "<c-ref>" --budget 1500 --data "<project>"`, затем задать вопрос: `deckmate project ask "<c-ref>" "Сцена порта должна выдавать 30 или 60 FPS?" --member "<member>" --to "<human>" --data "<project>"`.
2. Приостановить зависимую работу и следовать разделу [Вопросы и решения](#вопросы-и-решения): получить ссылку на вопрос, обсудить его, записать ответ, изменить целевой участок и отметить решение внесённым.

**Результат:** Открытый вопрос исключает Task порта из очереди; после ответа и внесения решения согласованный критерий 60 FPS записан, работу можно продолжить.

## review

**Когда:** Независимо проверить Task, выполненную другим участником.

**Просьба:** «Проверь результат экспорта по критериям готовности».

**Шаги:**
1. Прочитать `deckmate project brief "<c-ref>" --budget 1500 --data "<project>"` и указанные диапазоны, сопоставить отчёт и изменённые файлы с каждым согласованным критерием. Запустить необходимые проверки.
2. При нарушении критерия вернуть карточку: `deckmate project state "<c-ref>" not-started --member "<reviewer>" --reason "Expected 3 exported entries, got 2; include the third and rerun the export test." --data "<project>"`. Иначе записать рекомендацию через `deckmate project report "<c-ref>" --file "<review.md>" --member "<reviewer>" --data "<project>"`; до уполномоченной приёмки карточка остаётся в `review`.

**Результат:** Task либо возвращена с конкретным исправлением, либо остаётся в `review` с рекомендацией. Агент никогда не принимает собственную работу.

## audit

**Когда:** Проверить состояние одной колоды, Journey или всего проекта.

**Просьба:** «Проверь колоду выпуска приложения: что заблокировано и что давно не двигалось?»

**Шаги:**
1. Прочитать профиль, если он есть; выполнить `deckmate project map --data "<project>" --read-only`, `deckmate project summary --stale-hours 72 --data "<project>" --read-only` и `deckmate project find --deck "<deck-id>" --fields brief --limit 100 --data "<project>" --read-only`. Проверить признаки усечения и прочитать указанные источники.
2. Сохранить перечень и краткие приоритизированные предложения в отведённых файлах исследования; указать ссылки на карточки и основания в правилах. До изменений карточек получить согласование.

**Результат:** В отчёте, например, найдены Task выпуска без ответственного и заблокированная Task экспорта; до согласования доска не меняется.

## organize

**Когда:** Проверить раскладку доски или определить место новой сущности.

**Просьба:** «Проверь, в тех ли колодах находятся игровые объекты и производственные задачи».

**Шаги:**
1. Выполнить `deckmate project organize --data "<project>" --read-only` и прочитать диапазон источника `at` для каждой находки.
2. Предложить исправления без перемещения; три запроса на размещение приведены в разделе [Раскладка доски](#раскладка-доски). Создавать или перемещать только конкретные согласованные элементы обычным защищённым способом.

**Результат:** Например, список укажет на Hero дерева в колоде инструментов; автоматически ничего не перемещается.

## analyze

**Когда:** Изучить одну область игры по требованиям и подходящей линзе.

**Просьба:** «Чего не хватает нашим гоблинам, прежде чем делать других юнитов?»

**Шаги:**
1. Прочитать профиль, линзу юнитов и подходящие руководства жанра и движка; сообщить об отсутствии профиля или линзы. Выполнить `deckmate project find "units" --fields brief --limit 20 --data "<project>" --read-only` и `deckmate project brief "<c-ref>" --budget 1500 --data "<project>" --read-only`; прочитать указанные диапазоны.
2. Последовательно собрать данные исследования, кода и правил со ссылками на файлы или источники. Сравнить 2–3 варианта, рекомендовать небольшой прототип с критериями успеха и остановки и сохранить краткий вывод.
3. Только после согласования создать конкретные предложенные Task, как в [plan](#plan), и перевести новые Task в обсуждение: `deckmate project state "<c-ref>" discussing --member "<member>" --data "<project>"`. Если проект доступен только для чтения, оставить предложение в отчёте.

**Результат:** Обоснованное предложение прототипа юнита; после согласования и при доступной записи его Task появляется в `discussing`.

## gdd

**Когда:** Организовать игровые правила и объекты как связанные Doc, Hero и Task.

**Просьба:** «Размести правила лазания и работу над гоблином на доске игрового дизайна».

**Шаги:**
1. Выполнить `deckmate project map --data "<project>"` и `deckmate project find "climbing" --fields brief --limit 20 --data "<project>"`. Проверить существующие проекции источников, чтобы связать их, а не дублировать.
2. Предложить общий Doc правил лазания и Hero гоблина с Task по дисциплинам; получить согласование. Если Doc отсутствует, создать его: `deckmate project create "Climbing rules" --kind doc --deck "<knowledge-or-mixed-deck-id>" --body-file "<rules.md>" --member "<member>" --data "<project>"`. Остальные отсутствующие согласованные карточки создать, как в [plan](#plan), затем связать Doc правил с Hero через интерфейс.
3. Проверить Hero, родителя и колоду каждой дочерней карточки через `deckmate project show "<hero-ref>" --data "<project>"` и `deckmate project show "<child-ref>" --data "<project>"`.

**Результат:** Общий Doc правил лазания и Hero гоблина со связанными Task по дисциплинам, без дублирования карточек источника.

## journey

**Когда:** Повторять одни и те же производственные шаги для нескольких объектов.

**Просьба:** «Используй нашу Journey юнита для гоблина, а потом для других юнитов».

**Шаги:**
1. Выполнить `deckmate project pipelines --data "<project>"`, `deckmate project pipeline "<p-ref>" --data "<project>"` и `deckmate project step "<p-ref>" "<step-id>" --data "<project>"`; использовать выданные ссылку и ID шага, проверить инструкции, ответственных, колоды и зависимости.
2. После согласования применить Journey в интерфейсе к существующему верхнеуровневому Hero гоблина, выбрав шаги и совместимые колоды. Если шаблон колоды уже создал шаги, проверить их вместо создания дублей.
3. Выполнить `deckmate project show "<hero-ref>" --data "<project>"` и проверить каждого потомка: родителя, версию Journey и зависимости. Выполнить созданную Task по маршруту [work](#work); завершить одного юнита в сборке до массового производства.

**Результат:** У Hero гоблина есть созданные Journey Task выбранных шагов; само назначение работу не запускает.

## playtest

**Когда:** Превратить запланированный или проведённый плейтест в разобранные и проверенные задачи.

**Просьба:** «Выясни, могут ли игроки пройти через порт без подсказки».

**Шаги:**
1. Согласовать вопрос, сборку, аудиторию и решение. После согласования создать Hero плейтеста: `deckmate project create "Harbor navigation playtest" --kind hero --deck "<asset-or-mixed-deck-id>" --member "<member>" --data "<project>"`.
2. Импортировать встроенную Journey `playtest` и применить её к Hero в интерфейсе; сопоставить роли с колодами Task/Mixed. Проверить созданные шаги через `deckmate project pipelines --data "<project>"` и `deckmate project step "<p-ref>" "<step-id>" --data "<project>"`; не создавать дублирующие Task шагов.
3. Записать наблюдения с указанием сборки и подтверждений; отправить Task сессии: `deckmate project report "<session-c-ref>" --file "<report.md>" --member "<member>" --state review --data "<project>"`. Разобрать каждое наблюдение с владельцем проекта и создать только согласованные исправления. Проверить исправление повтором исходного сценария и сообщить результат обратившемуся.

**Результат:** У Hero плейтеста есть Task сессии и решений; для подтверждённой ошибки навигации создана одна Task исправления или один Hero с Journey ошибки, но не оба варианта.

## team

**Когда:** Настроить состав участников, Hands и порядок проверки.

**Просьба:** «Настрой для приложения одного исполнителя и одного независимого проверяющего».

**Шаги:**
1. Согласовать зарегистрированных участников, обязанности и порядок приёмки. Обновить реестр через работающий интерфейс или защищённый HTTP, сохраняя существующих участников; без сервера следовать [маршруту team](../skills/deckmate/workflows/team.md).
2. Добавить согласованные Task в каждый Hand через интерфейс; проверить `deckmate project hand "<member>" --data "<project>"` и `deckmate project next "<member>" --data "<project>"`. Отдельный проверяющий изучает отчёт исполнителя; уполномоченный человек или guardian принимает работу по правилам проекта.

**Результат:** У каждого зарегистрированного участника виден Hand; одно назначение ответственного не поставило работу в очередь и не запустило её.

## Вопросы и решения

Пример диалога после записи вопроса о порте:

> Агент: «Сцена порта должна выдавать 30 или 60 FPS?»
>
> Человек: «60 FPS при 1280×720».

1. Задать вопрос: `deckmate project ask "<c-ref>" "Сцена порта должна выдавать 30 или 60 FPS?" --member "<member>" --to "<human>" --data "<project>"`. По умолчанию целевая карточка — та же; открытый вопрос блокирует её Task.
2. Результат указывает карточку, а не номер вопроса. Выполнить `deckmate project brief "<c-ref>" --budget 1500 --data "<project>"` и взять актуальную ссылку `c-…#N` из открытых вопросов. Вызвать MCP `question` `{"ref":"<c-ref#N>"}` и обсудить в чате вопрос, целевой диапазон и последние решения.
3. Только после ответа человека вызвать MCP `answer` `{"ref":"<c-ref#N>","rev":"<question.rev>","answer":"60 FPS при 1280×720","as":"<human>"}`, передав `rev` из ответа `question`. В ответе находятся `card` и `index` решения; нумерация вопросов `N` начинается с единицы и не является индексом решения.
4. Вызвать MCP `next` `{"member":"<member>"}`. Если раньше выдаётся другое ожидающее решение, сначала обработать его. Для этого решения изменить только выданный диапазон `target`: содержимое карточки — через интерфейс или защищённый HTTP, исходный файл — по маршруту назначенной работы.
5. Когда изменение внесено, вызвать MCP `apply_decision` `{"card":"<decision.card>","index":<decision.index>,"rev":"<decision.rev>","note":"Performance updated"}` со значениями из `next` (включая `rev`). Снова прочитать карточку через `deckmate project brief "<c-ref>" --budget 1500 --data "<project>"` и запустить затронутые проверки. Отдельная Task решения не создаётся.

**Результат:** В карточке записаны ответ и отметка о внесении, в целевом участке указан согласованный критерий; обычную работу можно продолжить.

## Раскладка доски

Каждый пример даёт рекомендацию без записи; фактические колоды и совпадения Hero зависят от доски. Прочитайте `readNext`, проверьте наличие колоды с тем же названием и получите согласование до создания или перемещения.

1. **Новая сущность:** «Куда положить юнита-гоблина?» Выполнить `deckmate project organize --about "Goblin unit" --data "<project>" --read-only`. Пример: Hero в колоде сущностей Units; существующий подходящий Hero использовать повторно, а не дублировать.
2. **Работа по дисциплине:** «Куда положить анимацию гоблина?» Если подходящий Hero гоблина уже есть, выполнить `deckmate project organize --about "Animate goblin" --data "<project>" --read-only`. Пример: Sub Card, связанная с Hero, в колоде Animation или другой совместимой колоде Task.
3. **Правило сущности:** «Где хранить правила передвижения гоблина?» При существующем Hero выполнить `deckmate project organize --about "Goblin movement rules" --data "<project>" --read-only`. Пример: Doc правил, связанный с этим Hero, в совместимой колоде знаний или Mixed, а не текст правил внутри Hero.
